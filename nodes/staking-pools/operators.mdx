This guide helps validators set up and manage staking pools to offer liquid staking services to their communities.

## Quick reference

### Key parameters

| Parameter                 | Range                                      | Purpose                                           |
| ------------------------- | ------------------------------------------ | ------------------------------------------------- |
| Validator Commission      | 0-20%                                      | Commission on incentive token distribution        |
| Protocol Fee              | 0-20%                                      | Fee on eligible staking-pool reward growth        |
| Minimum Effective Balance | ≥ 250,000 BERA (configurable)              | Activation threshold and full exit safeguard      |
| Minimum CL Deposit        | 10,000 BERA                                | Smallest consensus-layer deposit the pool batches |
| Withdrawal Delay          | 129,600 blocks (≈3 days at ~2s block time) | Time before withdrawals can be finalized          |

Set your pool's minimum effective balance with `setMinEffectiveBalance()` on the SmartOperator. The on-chain floor is 250,000 BERA; when the validator set is full, the consensus layer may require more than that minimum.

### Key roles

| Role                                | Controls              | Function                               |
| ----------------------------------- | --------------------- | -------------------------------------- |
| `VALIDATOR_ADMIN_ROLE`              | All other roles       | Grant/revoke operational roles         |
| `REWARDS_ALLOCATION_MANAGER_ROLE`   | Reward allocation     | Direct PoL incentives to applications  |
| `COMMISSION_MANAGER_ROLE`           | Commission rate       | Adjust validator commission (0-20%)    |
| `PROTOCOL_FEE_MANAGER_ROLE`         | Protocol fee          | Adjust protocol fee percentage (0-20%) |
| `INCENTIVE_COLLECTOR_MANAGER_ROLE`  | Payout amount         | Adjust incentive collector payout      |
| `VALIDATOR_ADMIN_ROLE` (delegation) | Delegation operations | Manage delegation handler actions      |

### Essential functions

Core lifecycle and PoL reward allocation:

| Function                     | Contract      | Purpose                      |
| ---------------------------- | ------------- | ---------------------------- |
| `setMinEffectiveBalance()`   | SmartOperator | Set activation threshold     |
| `queueValCommission()`       | SmartOperator | Queue commission rate change |
| `queueRewardsAllocation()`   | SmartOperator | Queue reward allocation      |
| `setProtocolFeePercentage()` | SmartOperator | Set protocol fee rate        |

Protocol fee accrual (same percentage applies to both tracks during migration):

| Function                  | Contract      | Purpose                                                                                                                        |
| ------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `accrueEarnedWBERAFees()` | SmartOperator | Accrue protocol fees on **WBERA** balance growth — primary path after PoL Next.                                                |
| `accrueEarnedBGTFees()`   | SmartOperator | Accrue protocol fees on remaining **BGT** balance — **legacy / transitional** until BGT allowances are exhausted on your pool. |

Manual lever for compounding operator WBERA into pool assets:

| Function           | Contract    | Purpose                                                                                                       |
| ------------------ | ----------- | ------------------------------------------------------------------------------------------------------------- |
| `processRewards()` | StakingPool | Pull buffered staking rewards and any operator-held WBERA into the pool. Permissionless; callable by anyone. |

Compounding also runs automatically when stakers deposit through the pool's public deposit path and when withdrawals pull from operator-side WBERA. See [Automatic WBERA flows](#automatic-wbera-flows) below.

Legacy incentive surface (kept for transition; see [Deprecated BGT entry points](#deprecated-bgt-entry-points)):

| Function              | Contract      | Purpose                                                                                                                                                                 |
| --------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `claimBoostRewards()` | SmartOperator | **Legacy:** forward **BGT-era** boost incentive claims toward **`IncentiveCollector`**. Prefer WBERA-native operator flows for ongoing activity; treat as transitional. |

## Prerequisites

Before setting up a staking pool, ensure you have a fully operational Berachain validator node. You'll need at least 10,000 BERA to register the pool, though activation requires at least 250,000 BERA. See the [Validator Lifecycle](/nodes/architecture/validator-lifecycle) and [Become a Validator](/nodes/guides/become-a-validator) guides.

<Warning>
  Staking pools follow the standard Berachain validator lifecycle. After deployment, your validator
  will progress through the Deposited → Eligible states, but activation to the Active state depends
  on the ValidatorSetCap and your validator's priority relative to other validators.
</Warning>

## Validator lifecycle

Your staking pool integrates with Berachain's validator lifecycle. For details on validator states (Deposited, Eligible, Active, Exited, Withdrawn) and transitions, see the [Validator Lifecycle documentation](/nodes/architecture/validator-lifecycle).

The key consideration for staking pools is ensuring sufficient stake for activation. See [Setting minimum effective balance](#setting-minimum-effective-balance) below.

## Key terms and concepts

- **Active Threshold**: The point at which your pool has sufficient stake to activate the validator. When the active threshold is reached, your validator enters a cooldown period before activation.
- **Minimum Effective Balance**: The minimum stake amount required for validator activation and a safeguard that triggers full exit if deposits fall below it. You configure this on your SmartOperator; the floor is 250,000 BERA. When the validator set is full, the consensus layer minimum may sit 10,000 BERA above the lowest active validator.
- **Withdrawal Delay**: 129,600 blocks (≈3 days at ~2s block time) that must pass after a withdrawal request before it can be finalized.
- **Cooldown Period**: After the active threshold is reached, there is a cooldown period before the validator activates.

## Pool valuation and the accounting oracle

A pool's stBERA share price follows what the pool reports as total assets. The largest component is the validator's consensus-layer balance, which the chain learns through periodic verified reports from the shared **AccountingOracle**.

Between reports, the published share price reflects the **last verified** consensus-layer balance plus any execution-layer funds already in the pool. It does not move every slot with live beacon state. Stakers should expect the price to step when a new verified report lands, not continuously with every consensus-layer change.

See [Smart Contract Reference](/nodes/staking-pools/contracts) for oracle addresses on each network.

## Yield model

After the May 2026 PoL upgrade, per-block validator emission is a **flat fixed rate** (no boost curve).
Pools no longer differentiate on attracted BGT delegation; what you control is:

- **Validator reward allocation (cutting board)** — direct emissions to vaults you and your community care about. See [Manage Reward Allocations](/nodes/guides/manage-reward-allocations).
- **Incentives attracted to vaults you allocate to** — protocols still incentivize specific Reward Vaults; a strong allocation strategy increases incentive yield to your stakers.
- **Validator commission on incentive tokens** — capped at 20%, denominated in the WBERA-era incentive flow. See [Manage Validator Incentives Commission Rate](/nodes/guides/manage-incentives-commission).

Validator emissions accrue as \$WBERA on your `SmartOperator`. Protocol fees on the WBERA track settle when you change fee settings, when rewards move, or when you call `accrueEarnedWBERAFees()` to force a settlement pass. The legacy BGT fee track only matters while your operator still holds chargeable BGT; once that is exhausted, BGT fee accrual does nothing.

## Automatic WBERA flows

Operator-side WBERA is liquidity your pool can use without waiting for a consensus-layer exit. The contracts move it automatically in three common situations:

- **Compounding into pool assets** — When stakers deposit through the pool's public path, or when anyone calls `processRewards()` on the StakingPool, operator WBERA and buffered staking rewards roll into the pool's assets and lift the share price for every staker.
- **Covering withdrawals** — When a staker requests a withdrawal, the vault may pay part or all of it from operator WBERA already on the execution layer. Whatever remains is requested from the consensus layer. If operator liquidity covers the full amount, the staker still waits the normal finalization delay, but less balance has to exit the validator on the consensus layer.
- **Full exit sweep** — Triggering a full exit pulls any idle operator WBERA into the pool before the pool forwards its native balance to the withdrawal vault.

You do not need to call anything for these flows to run during normal deposits and withdrawals. `processRewards()` is the optional lever when you want to force a compounding cycle without waiting for the next staker deposit.

## Configuration

### Commission rates

You can set commission rates within 0-20%. Commission applies to the distribution of incentive tokens from Proof of Liquidity rewards. For step-by-step instructions, see [Manage Validator Incentives Commission Rate](/nodes/guides/manage-incentives-commission).

### Reward allocations

Direct PoL incentives to specific applications. For instructions, see [Managing Validator Reward Allocations](/nodes/guides/manage-reward-allocations).

### Setting minimum effective balance

The minimum effective balance gates validator activation and triggers a full exit if the pool falls below it. The on-chain floor is **250,000 BERA**. Set your pool's threshold with `setMinEffectiveBalance()` on the SmartOperator so it matches what the consensus layer requires. When the validator set is full (69 validators), the required minimum may rise in steps of **10,000 BERA** above the lowest active validator. Check the current lowest active stake on [Berachain Hub](https://hub.berachain.com/boost/).

## Routine operations

- **Monitor pool status**: Track whether your validator is active, how much the pool reports in total assets, and whether the active threshold is reached. Watch operator-side WBERA if you rely on it to cover withdrawals.
- **Delegation operations**: Manage delegations as needed. PoL Next accrues validator emissions as **\$WBERA** on your SmartOperator. Prefer **`accrueEarnedWBERAFees()`** for ongoing protocol-fee settlement; use **`accrueEarnedBGTFees()`** only while legacy BGT remains on the operator.
- **Emission token context**: PoL Reward Vault emissions are distributed in **\$WBERA**.
- **Protocol fee**: Set via `setProtocolFeePercentage()` (up to 20%). Changing the rate settles accrued fees on both tracks before the new percentage applies.

## Deprecated BGT entry points

The May 2026 PoL upgrade deprecates the BGT-era surface on `SmartOperator`. Per-block emission no longer scales with BGT delegation, so boost-management calls have no effect on yield. Berachain recommends winding down BGT positions held on your operator (unboost, drop-boost, redeem) and running WBERA-native flows instead: reward allocation, `accrueEarnedWBERAFees()`, and the WBERA incentive path.

The following entry points remain callable during transition but become inert once chargeable BGT is exhausted:

- `queueBoost()`, `activateBoost()`, `queueDropBoost(uint128)`
- `claimBgtStakerReward()`
- `claimBoostRewards(...)`
- `accrueEarnedBGTFees()`

## Withdrawal system

The shared **`WithdrawalVault`** is a per-chain singleton that finalizes withdrawal requests for every staking pool. Three situations matter for operators and stakers:

- **Short-circuit** — pool not yet at the active threshold. Liquidity comes only from execution-layer funds already in the pool. Inactive validators cannot withdraw through the consensus layer, so this path never issues a consensus-layer request.
- **Standard consensus-layer withdrawal** — the request exits stake from the validator on the consensus layer after the normal delay.
- **Operator-side WBERA cover** — at request time, the vault may pay part or all of a withdrawal from operator WBERA on the execution layer. Coverage can be full (nothing more leaves the consensus layer and the EIP-7002 fee is refunded), partial (the remainder still exits on the consensus layer), or none when operator liquidity is empty.

**What coverage means for stakers:** When your pool holds operator-side WBERA, a staker's withdrawal can be satisfied partly or wholly from that liquidity at request time. The staker still waits the same finalization delay, but less of their balance has to leave the validator on the consensus layer.

**Post-exit pools:** Once the validator has fully exited, withdrawal handling skips activation-era gates. BERA already sits in the vault; requests proceed without re-entering cooldown logic.

**Finalization delay:** Every request waits **129,600** blocks (≈3 days at ~2s block time) after submission before it can be finalized, regardless of whether operator WBERA covered part of the request. Coverage changes where the BERA comes from, not how long the staker waits.

**Retrying a full exit (`retryFullExit`):** After a full exit is triggered, the pool marks the validator fully exited and the vault submits a consensus-layer full exit. If that request fails or is dropped, anyone can call **`retryFullExit(pubkey, maxFeeToPay)`** on the shared `WithdrawalVault` to submit another attempt, paying up to `maxFeeToPay` for the EIP-7002 fee. It works only when the validator is already marked fully exited and no partial withdrawal is still in flight (roughly the last **49,153** blocks). Use this to recover a stuck post-exit consensus-layer sweep; normal staker withdrawal requests do not use it.

## Building your front-end

Your front-end should:

- Display withdrawal status and when each request can be finalized (use `getWithdrawalRequest(requestId)` and `requestBlock + 129600`).
- Support batch finalization with `finalizeWithdrawalRequests([...])`.
- Show staker balance, share price, and total rewards (e.g. via `previewRedeem(shares)`).

Berachain provides a React-based example template in the [guides repository](https://github.com/berachain/guides/tree/main/apps/staking-pools/frontend). Use `generate-frontend-config.sh` from `install-helpers` to generate `config.json` from your environment.
